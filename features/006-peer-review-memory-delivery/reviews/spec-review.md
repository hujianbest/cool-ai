## Findings

- [严重] `FR-1`～`FR-3`、`FR-11`～`FR-14`（尤其第 53～67、73～76、155、163、172、182～188 行）: 规格只有“不满足材料时不调用复核 Agent”、迟到结果和审计条目，却没有一条正向端到端验收标准证明 owner 能发起/继续一次真实的非执行者 Agent 复核、合格 Agent 实际读取冻结公开材料并产生结构化裁决；多名合格复核者时由谁领取/选择、调用失败/格式无效/用量失败后 owner 如何可见地重试也未定格。按现文可用人工直接提交裁决的实现通过大部分验收，却未闭合 backlog S-6“非执行者 Agent 能复核各子任务”的核心演示判据，也无法证明平台没有充当隐藏裁决者。→ 增加不泄漏 HOW 的可观察正向链路及失败/重试边界：从 owner 可执行入口或明确的项目内领取开始，到真实 Agent 调用、公开材料版本、公开输出、三选一裁决与审计闭合；明确多名候选时的 owner/Agent 边界，并禁止 owner、平台或客户端伪造 Agent 裁决。

- [严重] `FR-4`、`FR-5` 与第 42、84～96、216 行: “退回后执行者产生新的已合入结果”和“补充证据后再次独立复核”在现有 S-5 事实契约中没有可达路径。S-5 `FR-2`/`FR-12` 把 `merged` 设为不可继续、不可重试的终态，当前 `work_item_execution_results` 也只有不可变的 `awaiting_review` 结果；本规格同时声明不修改 S-5 保证，却未说明退回/补证怎样产生新的当前结果。升级补证还可能让同一结果先有 `升级`、后有第二个裁决，与 `FR-3`/`NFR-1` 的唯一有效裁决语义冲突。→ 明确返工和补证的可观察事实链：哪些 owner 回答必须回到返工、何时允许为同一任务创建新的 execution/结果版本、旧 merged 结果如何只读保留、补充证据是否必然形成新结果版本，以及每一结果版本究竟允许一个还是多轮裁决；同步消除与 S-5 终态契约的冲突。

- [严重] `FR-3`～`FR-7`、`FR-10`～`FR-12`（第 69～116、145～166 行）: 退回、升级、通过、升级已回答、任务重开、交付失效之间缺少一套互斥且完备的可观察状态语义。现有代码仍允许 owner 通过通用看板接口把 `in_progress` 直接改为 `done`，而规格没有专门验收所有既有写入口均不能绕过复核；“升级回答后补证”“通过后依赖变化”“最终交付生成失败/重试”也未明确此时哪个裁决、任务状态、使命完成状态和当前交付仍有效。结果可能同时显示 `done` 与未通过、已升级与可再次裁决、使命完成与当前交付失效，违反唯一事实源和“任何可观察部分完成状态数=0”。→ 在 WHAT 层列出各层互斥状态/有效性关系和触发后的可观察结果，并补充针对 owner 直接完成、旧 API/重放、升级回答、依赖重开、摘要生成故障与重启恢复的 Given/When/Then；明确任何写入口都必须服从同一完成门槛。

- [一般] `FR-8`、`FR-9`、第 120～136、214～220、225～231 行: 五类记忆的“来源”和“创建责任”没有与既有事实契约闭合。当前 S-3 仅支持四类、`owner_input | work_item | artifact_path` 三种来源且 `createdBy=owner`；规格新增经验并提到任务、裁决、验证证据、产物来源，却未明确 S-6 自动条目的公开创建 actor/责任归属、各来源引用必须绑定的精确版本，以及既有 owner 条目和新 Agent/系统条目如何一致展示。→ 定格五类均需展示的最小来源与责任字段；明确自动候选由哪个公开 actor 提议、由哪个复核裁决确认、平台仅持久化而不冒充业务作者，并要求任务/结果/裁决/验证/产物来源引用固定到可导航的历史版本。

- [一般] `FR-9`（第 128～136 行）: 去重键中的“正文和来源均相同”仍不可判定，未说明前后空白、Unicode 等价文本、同一来源的不同引用形式和来源版本是否算相同；“同一来源内容变化”也没有要求显式指明被取代的 active 版本。不同实现可分别创建、复用或取代，均声称符合现文，并发验收无法建立唯一预期。→ 给出有真实出处的确定性等价边界（不要发明容量/相似度阈值），明确来源身份是否包含来源版本，且替代必须显式关联唯一 active 前版；覆盖重试、并发、补充而非替代、跨类型和历史来源失效的判定样例。
