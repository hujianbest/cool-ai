## 1. 用户、领域与问题

**目标用户**是独自推动真实产品从想法走向交付、会配置模型服务，但不想亲自充当调研、设计、开发与复核 Agent 之间“路由器”的独立产品创造者。

“独立产品创造者”定义的是产品领域，不等于“只维护代码仓库的人”。项目可以产出调研、规格、设计、内容、流程、证据或软件。当前交付的 Windows verified workspace 是软件与文件成果的一种 Adapter 能力：它为绑定工作区内的受控读取、执行和合入提供安全边界，但不把 Project、Mission、Thread、知识或交付等产品概念缩减成仓库概念。Owner 通过打开本机文件夹进入或恢复 Project（D-47）；文件夹是绑定根，不是 Project 本身。

要解决的核心问题：

- 多模型协作依赖 owner 手工复制上下文、分派下一棒并汇总分散成果。
- 角色身份、公开协作历史、来源和决定容易随会话丢失。
- Agent 获得真实执行力后，越界、重复动作、陈旧结果和未经复核的交付难以控制。
- 知识、运行证据和外部能力若各自建立事实源，会让 owner 无法判断“什么是真的”。

## 2. 核心价值

- **单一 owner，平等角色 Agent**：owner 对方向、安全授权和人工判断拥有最终决定权；Agent 没有永久上下级，平台也不充当隐藏的总管 Agent。
- **公开协作而非私密编排**：目标、消息、交棒、决定、执行结果和复核结论进入可见、可追溯的项目事实。
- **真实能力受治理**：Provider、工作区、进程或外部工具只有在明确能力与安全边界内才能被使用。
- **来源先于结论**：成果、知识和回放必须指向冻结来源；不得用“最新”实体替代明确选择的来源。
- **复核后交付**：执行者不能独自宣布成功，合格非执行者的真实复核与验证证据构成交付闭环。

## 3. 第一性原理（可感知作业系统）

Cool AI 的定义落到用户可感知表面时，只证明三件事：

1. **有工作对象**：用操作系统文件夹选择器打开文件夹，进入或恢复 Project（不手输路径）。
2. **有作业班组**：系统提供规划 / 实施 / 复核三名自带 Agent（模板落地为真实 Agent）。
3. **有公开作业面**：中间是会话与 composer；工具结果在对话流中。使命、记忆、审批、审计是能力，不是主路径常驻面板，由图标轨按需打开。

阶段 1 只暴露作业面；治理能力不从产品定义中删除。交互可参考 pi 与 DeepSeek Harness 的 session + chat 信息架构，不复制其品牌或资产。完整交付顺序见开发计划 P0–P5。

## 4. 当前已交付事实

以下是截至 2026-08-15 已 ship 的现实，不代表规划中能力已经存在。细节与证据见特性分解清单。

- 本地单 owner Web 应用已持久化 Provider、Skill、Agent、Project、Mission、Work Item、协作、执行、复核、记忆与交付事实。
- owner 可用系统文件夹选择器打开/恢复项目，也可在未选项目时进行 1:1 聊天；已验证 Provider 下可配置稳定角色 Agent，并绑定本地 Windows 工作区。
- 协作驾驶舱支持 owner 公开发言、@Agent、真实模型接力、结构化消息与就地决策、回复引用、草稿、图片附件、持久线程与可恢复时间线。
- 会话整理已交付收藏、项目内搜索、标签批量整理、回收站、消息队列与受控 steer。
- Mission 看板仍是任务、依赖、负责人和状态的唯一业务边界；已交付依赖洞察、SOP 状态投影与派发租约。独立任务可在隔离执行中并行推进。
- Windows x64 的 verified-handle、sandbox、审批、验证、冲突检测与 merge journal 已为绑定工作区执行提供明确但非 OS 级恶意代码沙箱的安全边界。统一审批中心、按域审计与运行时间轴已交付。
- 非执行者 Agent 可基于冻结材料复核；通过后形成来源明确的记忆和最终交付。记忆检索与只读能力画像已交付核心。
- 统一设置入口、亮暗主题、渐进式首次使用引导、最小权限浏览器通知与 PWA 已交付。
- P0 暖金会话优先壳层（图标轨 / 会话侧栏 / 居中聊天 / 治理按需视图）已实现，收尾项见开发进展。

## 5. 四个演进层

演进层表达产品能力的累积顺序，不是四个独立应用，也不是页面导航。用户可感知的交付顺序是开发计划的 P0–P5，与演进层一致但按“先闭环、再变厚”重排。

### 5.1 核心协作

让 owner 能配置平等角色 Agent、建立 Project 与 Mission、在持久 Thread 中公开协作，并通过 Work Item、交棒、决定和独立复核完成可追溯交付。

当前已交付基础闭环及会话整理能力。后续目标包括受控扩展表面上的会话体验加厚，而不是第二套任务真相。后续能力必须继续使用同一公开协作事实，不能建立私语。

### 5.2 可信执行

让 Agent 对真实成果采取动作，同时保持工作区隔离、verified-handle、sandbox、审批、operation/version/lease、验证、冲突处理和恢复协议。

当前已交付软件工作区的受限执行、只读浏览、统一审批与复核闭环。后续目标包括受控编辑/Git、策略内终端/预览和救援动作。任何新 Adapter 都不能降低既有安全门槛。

### 5.3 知识治理

把目标、决定、事实、产物、经验、运行证据与来源组织为可检索、可取代、可复核的项目知识，而不是把所有聊天自动当成记忆。

当前已交付带来源的结构化共享记忆、复核后沉淀与项目内检索。索引健康、集合、知识图谱、Agent 署名提炼、脱敏导出与只读回放仍是目标能力。

### 5.4 扩展运行时

在不改变核心事实与安全协议的前提下接入新的 Provider、CLI/ACP、MCP、通知、语音或能力包。

当前已交付 OpenAI-compatible Provider、本地文本 Skill 与本机浏览器通知/PWA。CLI/ACP、MCP、插件生命周期、能力市场、语音及更广运维能力均未交付，必须按受控端口和独立高风险切片推进。

## 6. 已确认边界

- 保持本地优先、单 owner；多人账号、云端托管、多节点分布式执行、移动端完整能力不在当前范围。
- 只纳入浏览器通知/PWA；飞书、Telegram 等外部 IM/连接器、定时 daemon、值班简报、Signals/协作研读/播客、外部社区发布和无人值守自动化不进入当前范围。
- 游戏、主动人格助手、多目标私语和 Agent 投票不纳入产品。
- 完整计费、配额结算和商业订阅不在当前范围；基础用量与运行限额不等于账单。
- 无限制 shell、越出绑定工作区的文件操作、绕过审批的发布/部署、未受控外部执行和任意进程内插件始终排除。
- 功能范围扩大不授权复制 Clowder AI 的名称、猫角色、商标、文案、源码、调色盘或视觉资产；只重新实现已确认用户结果与通用原则。

## 7. 设计原则

1. **事实有且只有一个 owner**：每类命令事实由一个逻辑子系统维护；页面、路由、投影和 Adapter 不能成为平行写入口。
2. **跨域结果显式协调**：跨子系统用户结果由 Application Workflow 编排，在需要时使用同一 SQLite 事务保持强不变量；Workflow 不替代子系统业务规则。
3. **垂直切片交付**：每个真正进入 `implement` 的切片围绕一个 actor、一个主要用户结果和一个主要架构单元形成可演示闭环，再拆为 RED/GREEN 票据。领域切片使用唯一主子系统/主领域 Capability；只改变 Application Workflow、入站/UI Adapter 或交付证据的非领域切片明确主领域 Capability 不适用，并列出消费的真实 Capability；跨多个 owner 的产品追踪别名必须先拆成满足上述规则的真正纵切，别名本身不得进入 `implement`。
4. **公开 Interface 而非内部穿透**：跨子系统只依赖公开能力与稳定契约，不直接依赖对方表、私有服务或 UI 状态。
5. **投影可重建、命令事实不可反推**：搜索、看板聚合、运维和回放可使用选择性事件投影；投影永远不成为命令事实源。
6. **安全边界组合而非口号**：能力声明、最小权限、verified-handle、sandbox、审批、脱敏、审计、复核和恢复共同构成边界；不得把其中一项宣传成全部安全。
7. **历史与来源不可伪造**：冻结 Source Tuple、不可变版本链和真实 actor 身份优先于便利的“最新状态”替换。
8. **可访问、可恢复、可解释**：关键交互覆盖 loading、empty、error、disabled、success 与 focus；失败关闭，未知写入对账，未知状态不伪造成成功。

## 8. 开闭原则的适用边界

适用：

- 对已有两个及以上真实实现、或存在明确外部信任接缝的 Provider、CLI、MCP、通知和存储/工作区 Adapter，核心通过窄 Interface 对扩展开放。
- 对公开事件 schema 和可重建读投影，可新增消费者而不修改命令事实 owner。
- 对稳定的结构化消息类型或能力声明，可在 allowlist、版本、迁移和失败关闭规则内扩展。

不适用：

- 不为假想替换提前抽象所有内部函数、数据库访问或领域对象。
- 不允许扩展修改 Project/Thread/Run ownership、Frozen Source Tuple、operation/version/lease、acquire/checkpoint/finalize、审批、复核或迁移不变量。
- 不允许插件、Adapter 或新消息类型直接访问任意数据库表、宿主路径、凭据、进程或网络。
- 开闭原则不是安全协议的免审通行证。新增实现仍需独立威胁边界、最小权限、失败关闭、审计、测试、复核与按风险审批。

## 9. 开发与交付方式

完整步骤、阶段目标、前后端拆分与验收以 [`development-plan.md`](./development-plan.md) 为准。规格层只固定五条纪律：

1. **先闭环、再变厚**：P0 全局设计基座 → P1 基本可用 → P2 会话基础 → P3 会话整理 → P4 可信执行与任务真相 → P5 知识与扩展。
2. **后端 API 契约先行**：每个新特性先定义并落盘路由、严格 DTO、schema（如涉及）、错误语义与失败关闭行为，配套领域测试；前端再提供对应交互与展示消费该 API。
3. **UI 从全局设计出发**：UCD 见 [`ui/UI设计.md`](./ui/UI设计.md)；视觉令牌见 [`ui/DESIGN.md`](./ui/DESIGN.md)（暖米 + 暖金）与 `app/tokens.css`。任何界面改动复用令牌与既有驾驶舱基础元素，不硬编码设计值，不在既有交互上无计划微调。
4. **治理收轨**：使命 / 记忆 / 审批 / 审计由左侧图标轨按需打开，主路径只留会话。
5. **验收纪律**：聚焦测试 → `tsc` → `build` → 真实渲染 / 浏览器冒烟 → 记录演示验收；全量套件只在收尾与最终确认运行。
